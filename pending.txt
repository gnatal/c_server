Gaps vs. an Express-like C framework
=====================================

[DONE] Lib/app separation
- lib/ = engine (connection, router, httpParser, response, json), builds to lib/libcexpress.a
- app/ = application (main.c, handlers.c/h), links against the lib

1. Middleware
- [DONE] app_use() / next() chaining: app-wide middleware pipeline (lib/middleware.h,
  MiddlewareChain in appTypes.h) runs ahead of route dispatch; each Middleware gets
  the chain and calls chain_next() to continue. Route Handlers remain terminal (no
  next access) - only app_use()-registered middleware participates in chaining.
  Still no path-scoping (app_use middleware is app-wide, runs on every request,
  including ones that end up 404ing) - that needs sub-router mounting (section 2).
- [DONE] Centralized error-handling middleware equivalent: chain_error(chain, status,
  message) is the ((err, req, res, next)) analogue - hands off to the app's single
  ErrorHandler (app_use_error), or falls back to res_status+res_send if none is
  registered. Only one error handler per app, not a chain of them.
  See lib/middleware_test.c for pipeline/error-handler tests, and
  app/middlewares.c (mw_logger, mw_body_size_guard, error_handler_json) for a real
  usage example wired up in app/main.c.
- [DONE] Per-route middleware: app_get_mw()/app_post_mw()/app_add_route_mw() attach
  an explicit Middleware[MAX_ROUTE_MIDDLEWARES] + middleware_count to a Route at
  registration time (app_types.h, router.c/h). dispatch() (middleware.c) walks
  app-wide middleware first, then the matched route's own middleware, then the
  handler - chain->index counts continuously across both arrays. A route registered
  via plain app_get/app_post still gets middleware_count 0 (no behavior change).
  Registering more than MAX_ROUTE_MIDDLEWARES truncates with a stderr warning
  rather than overflowing the fixed array, same as MAX_ROUTES/MAX_MIDDLEWARES.
  See tests/test_middleware.c and tests/test_router.c for pipeline-ordering/
  short-circuit/overflow tests, and app/main.c (mw_authenticate now scoped to
  just POST /echo/json instead of gating every route) for a real usage example.
- [DONE] Prefix-scoped middleware: app_use_prefix(&app, "/api", mw) (lib/middleware.h)
  registers app-wide middleware that only runs when req->path starts with that
  prefix at a segment boundary ("/api" matches "/api" and "/api/users", not
  "/apiary"). app_use(app, mw) is unchanged and equivalent to
  app_use_prefix(app, "", mw) (unscoped, runs on every request as before).
  App.middlewares now stores MiddlewareEntry{fn, prefix} pairs (app_types.h);
  chain_next (middleware.c) skips non-matching entries without invoking them.
  See tests/test_middleware.c (test_prefixed_middleware_*) and lib/CLAUDE.md.
  Still no full sub-router mounting (nested route tables) - that's section 2.

2. Routing
- [DONE] Sub-routers / route mounting at a prefix: Router (app_types.h) is a
  standalone route table built via router_get/router_post/router_get_mw/
  router_post_mw/router_use (router.c), mirroring app_get/app_post/app_get_mw/
  app_post_mw/app_use. app_mount(&app, "/api", &router) is the C analogue of
  Express's app.use('/api', router) - it flattens the router's routes into
  app->routes with the prefix prepended (a route registered at the router's own
  "/" mounts at the prefix itself, not "prefix/"), and registers the router's
  own middleware app-wide via app_use_prefix scoped to that same prefix, reusing
  the prefix-matching machinery from the bullet above. Routes/middleware are
  copied at mount time (flattened, not nested) - match_route/dispatch are
  unchanged, no nested-router support yet. See tests/test_router.c
  (test_app_mount_*) and lib/CLAUDE.md ("Sub-router mounting").
- [DONE] app_put/app_patch/app_delete (+ _mw variants) and their router_put/
  router_patch/router_delete (+ _mw) equivalents (router.c/h) - thin wrappers
  around app_add_route(_mw)/router_add_route(_mw) exactly like app_get/app_post,
  so PUT/PATCH/DELETE routes register and dispatch (incl. per-route middleware,
  path params, and mounting via app_mount) identically to GET/POST. See
  tests/test_router.c (test_app_put_patch_delete_*, test_router_put_patch_delete_*)
  and lib/CLAUDE.md ("Deny-by-default routing").
- No app_head/app_options wrapper - HEAD/OPTIONS aren't handled specially (no
  auto-HEAD-from-GET, no auto-OPTIONS), though app_add_route/router_add_route
  would take either method string directly if registered by hand.
- [DONE] Path matches but method doesn't -> now 405, not 404: match_route
  (router.c) is unchanged (still requires an exact method match, still returns
  NULL on mismatch), but dispatch() (middleware.c) now calls the new
  match_route_allowed_methods (router.c/h) whenever route is NULL to tell the
  two NULL cases apart - a completely unmatched path (0 other routes match)
  still falls through to the existing 404, while a path that matches at least
  one route under a different method now gets a 405 with an Allow: <methods>
  response header (comma-separated, deduplicated, in route-registration order)
  instead. This runs in chain_next's final fallback (after all app-wide/
  route middleware), so app-wide middleware still observes/logs the real
  eventual status. See tests/test_middleware.c
  (test_dispatch_returns_405_*) and tests/test_router.c
  (test_match_route_allowed_methods_*).
- [DONE] Wildcards and a query-string parser:
  - match_path (router.c) now treats a "*" pattern segment as a wildcard.
    Mid-pattern it matches exactly one path segment without capturing it
    (unlike ":name"); as the pattern's last segment it matches that segment
    and everything after it (a trailing catch-all), so a route registered at
    "/files/" plus a trailing "*" answers any path under "/files/" without
    matching "/files" itself (no segment there for "*" to match against).
    Wildcards go through the same match_route/dispatch path as any other
    route, including the 404-vs-405 split above. See tests/test_router.c
    (test_match_path_wildcards), lib/CLAUDE.md ("Route wildcards"), and
    app/main.c (GET /files/* -> handler_files).
  - req->query is still the raw, unparsed string (unchanged), but
    parse_http_request (http_parser.c) now also calls the new
    parse_query_string(req->query, req) - a pure function taking the query
    string as a const char* buffer - which splits it on '&' then '=' into
    fixed req->query_names/query_values arrays (MAX_QUERY_PARAMS cap, extra
    pairs dropped rather than overflowed, same pattern as MAX_ROUTES/
    MAX_PARAMS elsewhere; a key with no '=' gets an empty-string value
    instead of being dropped). req_get_query(req, name) (http_parser.c) then
    looks that array up by key, mirroring req_get_param. See
    tests/test_http_parser.c (test_parse_query_string), lib/CLAUDE.md
    ("Query-string parsing"), and app/main.c (GET /search?q=... ->
    handler_search).
- [DONE] URL-decoding of path/params/query: the new pure url_decode(src, dst,
  dst_size, decode_plus) (lib/http_parser.c/h) decodes %XX hex escapes always,
  and '+' to a space only when decode_plus is set (the
  application/x-www-form-urlencoded convention for query strings, not path
  segments). parse_http_request runs it over req->path (decode_plus = 0)
  right after the query string is split off, so req->path, route matching,
  and req_get_param (which captures from the already-decoded req->path) all
  see decoded bytes; req->query itself is unchanged (still the raw string),
  but parse_query_string now runs url_decode (decode_plus = 1) over both the
  key and value of every parsed pair, so req_get_query returns decoded
  values too. A malformed '%' escape (not followed by two hex digits) is
  copied through literally rather than decoded or dropped. Output is never
  longer than input, so decoding is done in place (dst == src) with no extra
  buffer. See tests/test_http_parser.c (test_url_decode, the encoded-path
  case in test_parse_http_request, and the decoded/malformed-escape cases in
  test_parse_query_string) and lib/CLAUDE.md ("URL decoding"). Does not
  attempt to special-case %2F in a path segment (it decodes to a literal '/'
  like any other escape, ahead of route-pattern tokenization on '/') - a
  request path containing an encoded slash can merge what the client intended
  as two segments into one before match_path ever sees it.

3. Request parsing
- [DONE] req_get_header(name) map: the new pure parse_headers(header_block, req)
  (lib/http_parser.c/h) splits req->headers (still stored as the raw blob, unchanged)
  on "\r\n" then the first ':' into req->header_names/header_values
  (MAX_HEADERS-capped fixed arrays, same shape as query/param parsing - a line
  with no ':' is skipped, extra headers past the cap are dropped rather than
  overflowing). req_get_header(req, name) (http_parser.c) looks the array up
  case-insensitively (strcasecmp - header field names are case-insensitive per
  RFC 7230) and returns the first match. Called from parse_http_request right
  after req->headers is filled. app/middlewares.c: mw_authenticate now reads
  Authorization via req_get_header instead of an ad-hoc strstr(req->headers, ...)
  scan - which also fixes a latent bug (strstr was case-sensitive on the header
  name; req_get_header isn't). See tests/test_http_parser.c (test_parse_headers,
  and the req_get_header assertions in test_parse_http_request) and
  lib/CLAUDE.md ("Header parsing").
- [DONE] Content-Type-gated body validation on PUT/PATCH: handler_update_user and
  handler_patch_user (app/handlers.c) now call a shared has_json_content_type(req)
  helper (req_get_header(req, "Content-Type"), prefix-matched against
  "application/json" so a ";charset=..." suffix doesn't break the match) before
  attempting json_parse on req->body - a malformed JSON body now gets a 400
  (same {"error": "..."} shape as handler_echo_json's existing json_parse+400
  pattern) instead of being silently accepted, but a non-JSON body (missing or
  different Content-Type) skips validation entirely and behaves exactly as
  before, so a client sending plain text or form data doesn't get an incorrect
  400. See app/CLAUDE.md.
- [DONE] Whole request no longer lives in one fixed BUF_SIZE=8192 buffer: headers
  and body are now bounded independently. Connection.in_buf (app_types.h) is
  heap-allocated (connection_create) rather than a fixed array - it starts at
  BUF_SIZE (still the hard cap on headers alone, unchanged - see the 431 entry
  below) and handle_readable (connection.c) grows it via realloc, once, straight to
  the exact capacity a request's declared Content-Length needs, whenever that
  capacity is exhausted AND a complete header block has already been seen (so
  growth can never mask an oversized-header attack). The new MAX_BODY_SIZE
  (app_types.h, 1 MiB) is the hard cap on how large a body can grow to - a
  Content-Length beyond it is rejected immediately (413, see below) without ever
  growing the buffer. Request.body (app_types.h) is now char* rather than a fixed
  array - parse_http_request (http_parser.c) mallocs it sized to exactly
  content_length+1 bytes; the caller (handle_readable) frees it right after
  dispatch returns. flush_connection shrinks in_buf back down to BUF_SIZE once a
  keep-alive connection goes idle again, so one large request doesn't permanently
  inflate a long-lived connection's memory footprint. This is NOT true incremental
  streaming to the handler - Handler is unchanged, still synchronous, still gets a
  fully-buffered req->body - it's the same shape as how express.json()/
  express.urlencoded() behave in a real Express app (buffer the whole body up to a
  configurable limit, then hand it to the route handler as one materialized value).
  See improvements.md for what true streaming would additionally require, and
  lib/CLAUDE.md ("Body buffering") for the full design. See
  tests/test_http_parser.c (the large-body case in test_parse_http_request) and
  tests/test_connection.c (test_handle_readable_large_body_grows_buffer,
  test_handle_readable_body_too_large_413).
- [DONE] Negative Content-Length is rejected with 400; a well-formed Content-Length
  that exceeds MAX_BODY_SIZE is now a distinct case, rejected with 413 Payload Too
  Large instead of being folded into the same 400 as a malformed one -
  extract_content_length (http_parser.c) returns two different negative sentinels
  (-1 malformed, -2 too large) so connection.c can tell them apart when picking a
  status. See lib/CLAUDE.md ("Body buffering").
- [DONE] Headers (or a request) that can never fit in BUF_SIZE now get a 431 and the
  connection is closed, instead of hanging forever waiting for bytes that can't arrive
  (was the slowloris-shaped gap noted below). This guard is specifically about
  headers now (see the buffer-decoupling entry above) - a body that's merely large
  (but within MAX_BODY_SIZE) no longer hits this at all, it grows the buffer instead.
- No chunked transfer-encoding, no multipart/form-data, no x-www-form-urlencoded, no cookies
- No idle/read timeout for a slow client that trickles a request in a byte at a time
  within the buffer limit (distinct from the now-fixed buffer-overflow hang above).
  This matters more now than it used to: a slow client can hold open up to
  MAX_BODY_SIZE (1 MiB) of server-side buffer per connection instead of BUF_SIZE
  (8KB), since a Content-Length within that range is never rejected purely for
  being large.

4. Response
- [DONE] res_set_header(res, name, value): generic response header API (lib/response.c/h).
  Repeated calls with the same name (case-insensitive) overwrite in place; Content-Length
  and Connection are rejected (reserved, computed by send_with_content_type itself);
  Content-Type may be overridden and takes priority over res_send/res_json's default.
  Backed by a fixed Response.headers[MAX_RESPONSE_HEADERS] array - extra calls past the
  cap are dropped rather than overflowing. See tests/test_response.c.
- Still no streaming/chunked response, no static file serving, no res_redirect, no
  cookie helper
- status_text() only covers 11 codes (200/201/204/400/401/403/404/405/413/431/500)
- [DONE] malloc in response.c (conn->out_buf) is now null-checked; on OOM the
  connection is dropped instead of writing through a NULL pointer

5. Concurrency & portability
- kqueue ties the engine to macOS/BSD; no epoll/IOCP backend
- Single-threaded, single-process - no worker/multi-core model
- app->connections[MAX_CONNECTIONS] indexes by raw fd number - wasteful, assumes fd < 16384
- No graceful shutdown (SIGTERM draining in-flight connections)

6. Security
- No TLS/HTTPS
- [DONE] Max-header/body guard: header-only BUF_SIZE overflow now returns 431, a
  malformed (negative) Content-Length returns 400, and a well-formed Content-Length
  beyond the new MAX_BODY_SIZE cap (1 MiB, decoupled from BUF_SIZE) returns 413
  (see section 3)
- No Transfer-Encoding awareness (chunked bodies aren't supported at all yet)

7. Testing & DX
- [DONE] Comprehensive test binaries across all engine components (run via `make test`):
  - lib/json/json_test.c: JSON parser, value types, and serializer
  - lib/middleware_test.c: middleware pipeline (ordering, short-circuiting, 404 fallthrough, chain_error/ErrorHandler)
  - lib/router_test.c: router matching logic (literal paths, param capture, max params, route matching order, max routes)
  - lib/http_parser_test.c: HTTP parsing & edge cases (extract_content_length, request_is_complete, request_wants_close, parse_http_request, status_text)
  - lib/connection_test.c: connection handling & socket I/O using socketpair(2) (round-trips, keep-alive persistence, partial reads, 400 Bad Request, 431 Request Header Fields Too Large, Connection: close)
- [DONE] Request logging middleware (morgan-style): mw_logger (app/middlewares.c),
  registered via app_use in app/main.c, logs "METHOD PATH -> STATUS" once the rest
  of the pipeline has produced a final response.
- [DONE] Runtime config: server port is configurable via PORT environment variable
  (stored in App.config.port, falling back to DEFAULT_PORT 8080); API authentication
  key is configurable via API_KEY environment variable or mw_authenticate_set_key()
  (falling back to default secret).

Suggested order: [DONE] middleware system, then routing/request/response improvements
that build on top of it, then the rest as needed.
