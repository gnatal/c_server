httpServer.c - build & test instructions
=========================================

1. Compile
   ---------
   make

   (This runs: gcc-16 -Wall -Wextra -std=c11 -o httpServer httpServer.c
   httpParser.c router.c response.c connection.c handlers.c
   json/jsonParser.c json/jsonValue.c json/jsonWriter.c - see the Makefile.
   Plain `gcc` on this machine is aliased to a clang/SDK combo that fails to
   link right now - the Makefile uses gcc-16, installed via Homebrew,
   instead. No -lpthread needed: the server is single-threaded, using
   kqueue for I/O readiness - the same model Node.js/libuv uses under the
   hood on macOS.)

   Other Makefile targets:
   make run    - build (if needed) and start ./httpServer
   make test   - build and run the JSON parser's test suite
   make clean  - remove build artifacts (httpServer, json/json_test)

2. Run
   ---------
   ./httpServer

   You should see:
   Listening on port 8080

   Leave this running in its own terminal. Open a second terminal for the
   requests below. Stop the server with Ctrl+C when you're done.

3. Test the example routes (run in a second terminal)
   ---------
   # Home route -> 200, plain text welcome message
   curl -i localhost:8080/

   # Path param route -> 200, body echoes the captured :id
   curl -i localhost:8080/users/42

   # POST route -> 200, body echoes back whatever you POST
   curl -i -X POST -d "hi there" localhost:8080/echo

   # JSON POST route -> 200, body parses and re-serializes the JSON you POST
   curl -i -X POST -H "Content-Type: application/json" -d '{"name":"Ada","n":42}' localhost:8080/echo/json

   # Malformed JSON -> 400, body is {"error": "<parse failure message>"}
   curl -i -X POST -H "Content-Type: application/json" -d '{bad json' localhost:8080/echo/json

   # Unknown route -> 404 Not Found
   curl -i localhost:8080/nope

4. Check latency
   ---------
   time curl -s localhost:8080/

   Expected: well under 1ms of "real" time for the request itself (ignoring
   curl's own startup cost). If you see ~10ms+, something is forcing an
   extra TCP round trip (Nagle's algorithm was the culprit before the
   writev()/single-write() fix - see git history if it regresses).

5. Test concurrency (single thread, event loop - not one thread per connection)
   ---------
   Fire several requests at once and confirm they all come back correctly
   even though only one OS thread is running:

   for i in 1 2 3 4 5; do curl -s localhost:8080/users/$i & done; wait

   Expected: five lines like "User id: 1" .. "User id: 5" (order may vary).
   This works because the server never blocks on one connection - it uses
   non-blocking sockets and kqueue to interleave many connections on a
   single thread, the same way Node.js's event loop (libuv) does.

6. Test keep-alive
   ---------
   # Default HTTP/1.1 request -> response header should say "keep-alive"
   curl -i localhost:8080/ | grep -i connection

   # Explicit close -> response header should say "close", connection ends
   curl -i -H "Connection: close" localhost:8080/ | grep -i connection

   # Two requests over ONE connection - curl should report reusing it
   curl -v localhost:8080/ localhost:8080/users/1 2>&1 | grep -i "re-using\|connection"

   Expected: first case says "keep-alive", second says "close", third shows
   "Re-using existing connection" for the second request instead of a fresh
   connect.

7. Load test (optional, needs `wrk`: brew install wrk)
   ---------
   wrk -t4 -c1000 -d10s http://127.0.0.1:8080/

   MAX_CONNECTIONS is 16384 and BACKLOG is 128 (the max macOS honors -
   `sysctl kern.ipc.somaxconn` - raising the constant further in code won't
   help without also raising that sysctl, which is a system-wide, sudo-gated
   change: `sudo sysctl -w kern.ipc.somaxconn=<N>`, not something this repo
   changes for you).

   With keep-alive, wrk reuses each of its N connections for the whole test
   instead of opening a new TCP connection per request, so `Socket errors:
   connect` should now stay at or near 0 even at `-c5000` (before keep-alive,
   that many new connections/sec exhausted macOS's 16384 ephemeral client
   ports well within their 30s TIME_WAIT window - a client-side port
   exhaustion artifact, not a server capacity problem). req/s should also be
   noticeably higher since the TCP handshake cost is now amortized across
   many requests per connection instead of paid on every single one.

   After a load test finishes, check `top` (or `ps -o %cpu -p $(pgrep
   httpServer)`) - httpServer should drop back near 0% CPU. If it stays
   pegged at 100%, that indicates a kqueue registration leak (an idle
   connection stuck registered for EVFILT_WRITE with nothing to send would
   spin the event loop) - worth flagging if you see it.

7b. Load test the JSON echo route (needs `wrk`: brew install wrk)
   ---------
   wrk's default GET-only mode can't send a POST body, so this route needs
   a small Lua script (scripts/wrk_echo_json.lua) that sets the method,
   JSON body and Content-Type header wrk applies to every request:

   wrk -t8 -c5000 -d15s -s scripts/wrk_echo_json.lua http://127.0.0.1:8080/echo/json

   This exercises json_parse + json_stringify + json_free per request, not
   just the HTTP path - it's the number to watch if you change anything in
   json/. Reference run on this machine: ~136k req/s, ~31ms avg latency at
   5000 connections (vs ~155k req/s and sub-ms latency for the plain-text
   route 7's `/` at similar concurrency - the gap is the JSON parse/stringify/
   malloc-heavy work per request, not the HTTP layer). A handful of "Socket
   errors: read" at c5000 is normal connection churn, not a server bug;
   watch instead for `timeout` errors climbing or Requests/sec collapsing,
   which would point at a real regression.

8. What "good" looks like
   ---------
   - Server prints "Listening on port 8080" and keeps running (doesn't exit).
   - Each curl above returns promptly and the server keeps accepting new
     connections afterward (it doesn't crash or hang).
   - 404s only happen for routes that were never registered in main().
   - `ps -M $(pgrep httpServer)` (or Activity Monitor) shows a single thread,
     confirming there's no thread-per-connection happening anymore.
   - httpServer's CPU usage sits near 0% at idle, even after connections
     have been through a full keep-alive request/response cycle.
